# Quickstart, troubleshooting and recovery

T05 covers documented manual procedures verified in disposable projects. There are no update, restore or uninstall commands. These steps apply to the guided snapshot installer on Linux/macOS; the [manual adapter installations](harness-adapters.md#installing-each-harness) use different ownership and removal procedures. Keep all installation records, paths and backups private.

## First run

Requires Node.js 22+, npm for npm commands, and Git. Bash and jq are needed for the Claude/Codex shell guard. Install prerequisites separately using their supported instructions; setup never installs tools or signs in. Start with one disposable project before applying to an existing project or your home directory.

1. Obtain a complete Construct Git checkout from the intended remote. In that checkout, run `node --version`, `git --version`, `npm run check` and `node scripts/setup.mjs --help`. Expect Node 22 or later, a successful adapter check and help without installation writes. `doctor` and `validate` remain specifications, not executable npm scripts.
2. From the intended target project, run the command below, replacing the source path. Choose **Current project**, the harnesses you need, **None for now** for services, and empty repository/folder references for a local trial. Review the target paths before confirming. No, EOF or Ctrl+C cancels before apply.
3. For an existing installation, first save a private inventory of existing destination entries, their types, contents or link targets, and permissions. Use the [destination table](guided-setup.md#snapshots-and-installed-resources), including any configured global roots. Review every OVERWRITE: it replaces the whole entry, including settings files; it does not merge preferences. Cancel if that is unsuitable. Preserve the inventory and any originals before proceeding.
4. Confirm Yes only for the reviewed plan. Expect `Applied … changes` and `.construct-setup/plan.json` in each target. If overwrites occurred, save the printed `restore.json` location. Open the plan locally and confirm harnesses, target, source revision and snapshot. Check a selected installed skill resolves into that target's `.construct-setup/snapshots/<content-id>/`, and that unrelated files and `.construct-setup/config.json` are unchanged.
5. Restart the selected harness and review its discovery/trust state as described in [guided setup](guided-setup.md#snapshots-and-installed-resources). File installation is complete only when the recorded resources exist and links resolve. Harness discovery, agent invocation, guard activation and service sign-in are separate checks; record each as unverified until observed in the intended harness. Do not test a guard by attempting a real push or post.

```sh
# Run from the target project, not the Construct checkout:
node /path/to/construct/scripts/setup.mjs
```

For a safe first use, load the Construct skill and ask the harness to summarize a synthetic local file without changing it. Success is a visible discovered skill and the requested read-only result. A copied agent profile alone does not establish agent execution. pi needs a separately installed subagent extension; Codex hooks need `features.hooks = true`, which setup does not set. Follow [tool preflight](tool-preflight.md) only when you actually need a service.

Keep `.construct-setup/` ignored, including before creating private configuration. From a Git target, `git check-ignore --no-index .construct-setup/config.json` should show the ignored path and `git ls-files -- .construct-setup` should show no tracked entries. Review `git status --short`: native harness resources outside the store may still appear as untracked files. Do not publish setup records or local snapshot paths. See [private configuration](private-configuration.md).

## Troubleshooting by symptom

Use the matching row before rerunning setup. Keep raw output local; share only sanitized symptoms and tool versions, without hosts, account details, private paths or credentials.

| Symptom | Checks | Recovery | Expected result |
| --- | --- | --- | --- |
| `node`, `git`, `npm`, Bash or jq is missing | Check `command -v` and the available tool's `--version`; distinguish setup prerequisites from guard prerequisites | Install through the tool's supported procedure yourself. Do not change global tools to diagnose an unrelated failure | Required tools are available; a missing guard prerequisite remains an activation blocker |
| Setup reports Windows is unsupported | Check the operating system | Use a supported Linux/macOS environment; do not assume native Windows compatibility | Setup help runs in the supported environment |
| `Unknown argument` | Run `node /path/to/construct/scripts/setup.mjs --help` | Use the interactive command without extra arguments; no update/uninstall flags exist | Help exits successfully without writes; an unknown argument exits 1 |
| Missing project, `ENOENT`, or path rejected | Confirm the entered directory exists; paths cannot contain commas in this wizard | Create or select the intended directory, then rerun; use `current` for the current project | Review displays the intended existing target |
| `Not a plain directory` | Inspect the reported entry and its parents without following links | Leave redirected/symlinked parents alone; choose a plain target or agree a separate migration | Planning succeeds without changing another installation |
| `Changed since review; rerun setup` | Check for another setup process or edits since the plan was displayed | Stop competing changes, preserve edits and review a new plan | Stale state is refused; the new plan reflects current contents |
| `OVERWRITE` would replace personal settings | Inspect the displayed replacement and current entry locally | Cancel. Preserve originals and decide whether to use a different scope or manually integrate resources | No writes on cancellation; no silent settings merge is assumed |
| `Already installed with these choices. No changes.` | Confirm target, harnesses and snapshot match the intended selection | No action for an identical run; for an update, check that the source resources actually changed | No writes or new backups for identical resources/choices |
| New checkout revision but installed content is old | Inspect the target's plan and native link targets | Follow the update procedure below; pulling the source does not update copied snapshots | Installed links point to the reviewed new snapshot |
| Deselected harness still appears | Inspect previously installed resources | Deselecting is not uninstalling; use the removal procedure below for that harness | Only reviewed resources for the removed harness cease being discovered |
| Skills/agents do not appear after apply | Check target scope, link resolution, harness configuration roots and trust; compare with the installed version's supported discovery mechanism | Restart/reload the intended harness. For pi, check the separate subagent extension; do not repeatedly overwrite configuration to fix discovery | Resources resolve; runtime discovery is separately observed or remains unverified |
| Guard does not prompt or cannot be confirmed active | Check Bash/jq, hook configuration, Codex hook enablement and higher-precedence OpenCode settings | Treat the guard as unverified; inspect supported harness diagnostics and use synthetic checks rather than executing outbound operations | No claim of enforcement until runtime evidence exists; missing jq can cause the shell guard to skip checking |
| Service was selected but sign-in fails | Selection records intent only. Distinguish network failure, authentication failure, wrong host/account and denied access using [tool preflight](tool-preflight.md) | Reuse a suitable existing method; if missing/unclear ask for the supported method and target, never a secret. Do not reset credentials automatically | Offline validity stays unverified; only an observed sign-in check establishes live validity |
| `Source link escapes checkout`, `Source link is not snapshot-local`, or incomplete checkout | Inspect source Git status, tracked resources and adapter consistency | Preserve source edits; repair the complete checkout and regenerate adapters only if intended. Never copy private directories to fill gaps | Source checks pass and snapshot planning uses only reviewed tracked resources |
| Permission denied or partial apply | Check access to the exact target and the reported recovery paths | Stop; preserve records and inspect the recovery procedure. Do not use sudo or recursive permission changes as a shortcut | Originals are restored automatically or specific remaining entries are identified for manual recovery |
| Setup was killed or reports manual recovery needed | Inspect `restore.json`, destination entries and which backup entries actually exist | Use the interrupted-run procedure below; do not assume every manifest row was processed | Each affected entry is accounted for, preserving both originals and newer edits |
| Backup missing, edited since install, or ownership unclear | Compare the private inventory, plan, saved mappings and current entry | Stop that entry's recovery/removal; retain both versions and ask for a decision | No guessed deletion or overwrite; unresolved work is recorded |

## Update an installation

1. Inspect the source checkout's status, remote and branch. Fetch the verified branch and inspect divergence before integrating. With a clean checkout and confirmed base, `git merge --ff-only <reviewed-remote-ref>` adopts the fetched revision without rewriting history. If there are local edits, divergence or an operation in progress, stop and reconcile deliberately using [git-workflow](../skills/developer/git-workflow/SKILL.md); do not stash, reset or force-push automatically.
2. Before setup, stop the relevant harness and record the target's current plan, selected scopes/harnesses, snapshot ID, native entries and any later user changes in a private inventory. Preserve `.construct-setup/config.json`. For global installs, record the configuration-root overrides actually used; changing an override creates a different destination and leaves the old installation in place.
3. Run the same setup command from the same target. Re-enter the intended choices; the wizard does not automatically load saved preferences. Review every changed destination and its replacement. Approve only after preserving conflicting local settings. Save each new recovery mapping. Old snapshots remain available; neither deselection nor an update cleans them up.
4. Confirm the plan's source revision and selected snapshot, resolve native links, compare unrelated configuration with the pre-update copy, and restart the harness. An identical rerun should print `Already installed with these choices. No changes.` without new backups. Content-identical source changes can reuse the same content ID even when the recorded source revision changes.
5. For rollback, use that update's mapping to restore overwritten native entries and the previous plan, preserving newer edits as below. Do not merely edit `plan.json` or delete the new snapshot: installed links, hook commands and pi package settings also select the snapshot. Remove only update-created entries whose ownership and unchanged state are established. Keep snapshots until no installation references them.

## Restore an overwrite or interrupted run

A mapping is a private JSON array of `{path, backup}` rows. Non-null `backup` names the original moved entry, which may be a file, directory or symlink. Null means no original existed for that entry in this run. A manifest is written only when at least one overwrite occurs; a clean install has no restore mapping. The current plan is not a complete ownership ledger, and it does not list native entries from all older runs.

1. Stop the affected harnesses and competing setup processes. Locate the exact run's `restore.json` under `.construct-setup/backups/`; multi-target runs can store the mapping under the first target while rows name other targets or configured global roots. Read it locally and verify every path against your saved targets. Do not execute paths from untrusted JSON.
2. Inspect each entry and its parents without following symlinks. For interrupted runs, a listed backup may not yet exist. If missing, do not delete the current destination or assume it is new. Leave the row unresolved until the current destination, original inventory and partial writes are understood. Automatic error rollback may already have restored originals; a killed process may not have.
3. Create a private recovery holding directory outside installed resource trees, using `umask 077` and `mkdir` for a new, nonexisting path. Move each current destination there before restoring its original. This retains newer edits and moves symlinks themselves rather than their referents. For a reviewed row with an existing backup, restore by moving the backup entry to its exact now-vacant original destination. Never restore onto an occupied destination.
4. For a null-backup row, move aside only an entry confirmed created by this run and safe to retire. In an interrupted run it may not have been written at all. Keep unrecognized or edited entries pending review. Handle native links/settings first; retain snapshot contents, backups, the ignore rule and private configuration while resolving references.
5. Verify original file bytes, modes, directory contents and link targets against the inventory, and confirm unrelated files and symlink referents stayed unchanged. On a complete update rollback, the previous plan and native resources must agree on the old snapshot. Restart and check discovery separately. Retain recovery evidence and the holding directory until the user has reconciled newer edits.

Example for **one reviewed row**, after confirming that its backup exists, parent directories are plain directories, and the holding name is vacant. Substitute exact private paths locally; these placeholders are not runnable as written:

```sh
# First create a fresh private holding directory outside resource directories.
# Move the current entry to a vacant holding name, then restore the original.
mv -i '/exact/native/settings.json' '/private/holding/settings-after-update.json'
# Continue only after confirming the first move succeeded and native path is absent.
mv -i '/exact/backups/run/entry' '/exact/native/settings.json'
```

Do not batch these commands over an unreviewed manifest. Moving the backup consumes that backup location; record where it went and do not replay the row. If any command fails, stop before the next move. `mv -i` does not replace checking directory destinations, parent links and current state.

## Remove Construct resources

Removal means retiring Construct's resources while retaining the user's harness installation, credentials, preferences and other plugins. It does not mean deleting `.claude`, `.opencode`, `.pi`, `.agents`, `.codex`, or the whole `.construct-setup` directory.

1. Stop the affected harness. Choose project/global scope and the exact harness to remove. Inventory current native links, hook/settings files and package references using the plan, resource table and every retained run mapping. Include older/deselected resources. Verify ownership by link target or reviewed file contents, not just a matching filename. For a clean installation without mappings, use the before-install inventory and inspect current resources; if origin is uncertain, leave the entry in place.
2. Create a private holding directory outside discovery paths. Move only confirmed Construct native entries there, one reviewed entry at a time. For files shared with other configuration, preserve the whole current file first, then manually remove only the Construct hook/package/permission entries. Restore an earlier backed-up original only if that is still the intended configuration; merge later user changes deliberately. Leave unrelated skills, agents, packages and settings in place. Keep Codex `config.toml` and its hook feature setting unless a separate decision changes it.
3. If undoing several updates, mappings represent successive versions. Review them newest to oldest; do not restore an earlier Construct version and mistake that for uninstalling. For a full removal, recover the pre-Construct original or reconcile the surviving user settings. A missing backup means restoration cannot be promised.
4. Restart the harness and inspect the relevant project/global discovery scopes. Success: removed Construct resources are no longer discovered from those scopes; unrelated resources and user configuration still work. A global or other project install can legitimately keep Construct visible. Verify those separately before declaring complete removal.
5. Retain `.construct-setup/config.json`, backups, inventory and snapshots by default. Only after inspecting all native links, hook command paths and pi package references across relevant targets may you separately retire an unreferenced snapshot. Do not automatically delete the store or holding directory. The retained plan is historical installation evidence, not proof that resources are still installed; keep a private note of what was removed.

Changing or removing the source checkout alone does not uninstall copied snapshots. Manual plugin/package installs and shell-profile changes made outside guided setup require the matching tool's supported removal procedure after checking its installed help; do not apply snapshot ownership assumptions to them.
